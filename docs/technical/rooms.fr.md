# Salles

[English](rooms.md) | Français

Comment les salles sont créées, lues et configurées par l'API : modèle de données, code et lien, réglages, endpoints, le lobby, et où cela se trouve dans le code. **Construit dans #83** (API), **#84** (écrans) et **#86** (jonction avec un compte) et **#87** (invités, §2.4). Ce qu'est une salle pour l'utilisateur : [user stories](../product/milestone-1/user-stories.fr.md) US-2.1 et US-2.2, [cycles de vie](../product/milestone-1/lifecycles.fr.md).

## 1. Vue fonctionnelle

Une salle est le lieu où un groupe joue, rejoint par son **code** ou son **lien**. Elle est créée à partir d'un des templates de l'utilisateur, qui en devient le **room admin**. Ses **réglages** s'appliquent à la partie suivante.

| Action                 | Endpoint                                          | Résultat                                                                                                                |
| ---------------------- | ------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| Créer une salle        | `POST /rooms`                                     | Une salle ouverte sur un de mes templates qui a au moins une tuile ; j'en suis le room admin et le premier participant. |
| Ouvrir une salle       | `GET /rooms/{code}`                               | La salle, ses réglages et ses participants, pour un participant.                                                        |
| Rejoindre une salle    | `POST /rooms/{code}/join`                         | Une place de joueur pour moi, avec mon nom affiché ; ma place si j'en ai déjà une.                                      |
| Rejoindre en invité    | `POST /rooms/{code}/guests`                       | Une place d'invité avec un pseudo, un cookie du navigateur et mon lien perso.                                           |
| Revenir en invité      | `POST /rooms/{code}/guest-session`                | Ma place d'invité, depuis le lien perso, sur n'importe quel appareil.                                                   |
| Nouveau lien perso     | `POST /rooms/{code}/guest-link`                   | Un nouveau lien perso pour l'invité reconnu par son cookie ; l'ancien cesse de marcher.                                 |
| Modifier les réglages  | `PATCH /rooms/{code}/settings`                    | Les nouveaux réglages (room admin seulement) ; pendant une partie, seulement les arrivées.                              |
| Retirer un participant | `DELETE /rooms/{code}/participants/{id}`          | Sa place supprimée (room admin seulement, pas sa propre place), à tout moment ; il peut rejoindre à nouveau.            |
| Bannir un participant  | `DELETE /rooms/{code}/participants/{id}?ban=true` | Retiré, et son compte (ou, pour un invité, son navigateur) ne peut plus rejoindre.                                      |
| Débannir               | `DELETE /rooms/{code}/bans/{id}`                  | La personne peut rejoindre à nouveau (room admin seulement).                                                            |

### Règles

- **Template** : un des miens, non supprimé, avec **au moins une tuile** (US-2.1). Sinon `404` `template_not_found` ou `409` `template_has_no_tiles`. Plusieurs salles peuvent utiliser le même template.
- **Code** : 6 caractères parmi `ABCDEFGHJKLMNPQRSTUVWXYZ23456789` (sans `0`, `O`, `1`, `I`, qu'on confond en lisant ou en dictant), aléatoire (`secrets`), unique. Il est lu sans tenir compte de la casse : `k7p2qx` ouvre `K7P2QX`.
- **Lien** : `FRONTEND_BASE_URL` + `/r/` + le code, par ex. `http://localhost:5173/r/K7P2QX`. La page elle-même arrive avec #84.
- **Room admin** : le créateur. Il a aussitôt une ligne **participant** : il compte dans la limite de participants même s'il ne joue pas (US-2.6).
- **Visibilité** : une salle n'est visible que de ses **participants**. Les autres reçoivent `404` `room_not_found`, exactement comme pour un code inconnu : l'API ne révèle jamais qu'une salle existe.
- **Rejoindre avec un compte** (US-2.4) : le code suffit, qui l'a peut rejoindre. `POST /rooms/{code}/join` donne à l'utilisateur une place de **joueur**, affichée avec son nom, sans étape de plus. Rejoindre à nouveau rend **la même place** (une place par utilisateur et par salle), room admin compris. Un code inconnu répond `404` `room_not_found`. La ligne de la salle est verrouillée pendant la jonction : deux jonctions simultanées du même utilisateur donnent une seule place ; la contrainte unique `(room_id, user_id)` reste le dernier filet.
- **Capacité** (US-2.6) : au plus `FREE_PLAN_MAX_PARTICIPANTS` (10) places par salle, room admin compris même s'il ne joue pas. C'est une limite du plan, une constante comme `FREE_PLAN_MAX_TILES`, pas un réglage. Les places d'invités expirées ne comptent pas. Un nouveau venu au-delà de la limite reçoit `409` `room_full` avec le param `max_participants`.
- **Verrou des arrivées** (US-2.10) : pendant une partie (statut `playing`), quand `late_arrivals_allowed` est désactivé, un nouveau venu reçoit `409` `room_locked`. Hors partie, le réglage ne bloque rien. Qui a déjà une place revient toujours (un compte par `POST /join`, un invité par son cookie ou son lien perso), même si la salle est pleine ou verrouillée ; un participant retiré est un nouveau venu. Contrôles de `join` et `join_as_guest`, sous le verrou de la salle : bannissement, place existante, verrou, capacité (`_ensure_can_arrive`).
- **Réglages** (US-2.2), avec leurs valeurs par défaut :

  | Réglage                 | Valeurs                            | Défaut                          |
  | ----------------------- | ---------------------------------- | ------------------------------- |
  | `item_order`            | `template`, `random`               | `template`                      |
  | `auto_advance`          | `none`, `timer`, `everyone_placed` | `none` (manuel seulement)       |
  | `timer_seconds`         | 5 à 300 s                          | `ROOM_DEFAULT_TIMER_SECONDS`    |
  | `cooldown_seconds`      | 10 à 600 s                         | `ROOM_DEFAULT_COOLDOWN_SECONDS` |
  | `admin_plays`           | `true`, `false`                    | `true`                          |
  | `late_arrivals_allowed` | `true`, `false`                    | `true`                          |

  `timer_seconds` est gardé même quand `auto_advance` n'est pas `timer` : la durée choisie revient si le timer est remis.

- **Seul le room admin** modifie les réglages (`403` `room_admin_required` pour un autre participant ; [permissions](../product/permissions.fr.md)).
- **Pendant une partie** (statut `playing`), les réglages sont bloqués, **sauf les arrivées** (US-2.10) : tout autre champ répond `409` `room_settings_locked`.
- **Modification vide** : un `PATCH` sans aucun champ (ou avec seulement des valeurs `null`) ne change rien.
- **Retrait et bannissement** (US-2.11, US-2.12) : le room admin retire un participant, à tout moment, partie comprise ; la place est supprimée et la personne peut rejoindre à nouveau, sauf si elle est bannie. Un compte banni ne peut plus rejoindre ; un invité banni n'est refusé que depuis le même navigateur (§2.5).
- **Suppressions** : la purge d'un template supprimé garde la salle, sans template (`template: null`) ; aucune nouvelle partie ne peut alors y démarrer. La suppression du compte du room admin supprime ses salles et leurs participants.

## 2. Conception technique

### 2.1 Options considérées

| Sujet            | Options                                                                 | Choix et raison                                                                                                                                                                                                                         |
| ---------------- | ----------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Réglages         | Table `room_settings` séparée (1-1) ; **colonnes de `rooms`**           | **Colonnes** : le modèle de domaine en fait une composition 1-1 de la salle ; des colonnes évitent une jointure et une ligne orpheline. L'API les regroupe quand même dans un objet `settings`.                                         |
| Verrou de partie | Attendre les parties (#91) ; **`status` open / playing dès maintenant** | **Statut dès maintenant** : la règle « bloqué pendant une partie » est construite et testée avec les réglages ; le démarrage (#91) ne fait que poser `playing`. « Fermée » n'est pas un statut : une salle fermée est supprimée (§2.6). |
| Code             | Séquentiel ; UUID ; **code court aléatoire**                            | **Code court aléatoire** : tapé ou dicté par les joueurs, impossible à deviner à partir d'autres codes. Une contrainte d'unicité et un nouveau tirage en cas de collision le gardent unique.                                            |
| Place de l'admin | Rôle seulement dans `rooms.admin_id` ; **ligne participant aussi**      | **Ligne participant** : l'admin compte dans la limite de participants même s'il ne joue pas (US-2.6), et sa place lui donne accès comme à tout participant.                                                                             |
| Adressage        | Par UUID ; **par code**                                                 | **Par code** : le [guide du temps réel](realtime.fr.md) adresse le canal de la salle et son instantané REST par code (`/rooms/{code}`).                                                                                                 |
| Jeton d'invité   | JWT signé ; **jeton opaque aléatoire, haché en base**                   | **Jeton opaque** : comme un refresh token (256 bits, seul le SHA-256 est gardé), une fuite de la base ne donne aucun jeton utilisable. Une place meurt avec sa salle (`ON DELETE CASCADE`), ce qui tue son lien.                        |
| Lien perso       | Jeton dans la query string ; **jeton dans le fragment**                 | **Fragment** (`/r/<code>#guest=<jeton>`) : un navigateur ne l'envoie jamais au serveur, il n'atteint donc jamais les journaux d'accès ; le frontend le lit et le retire de l'adresse une fois utilisé.                                  |
| Validité         | Glissante ; **fixe depuis l'arrivée**                                   | **Fixe** : `GUEST_LINK_TTL_DAYS` (30 au plus, comme l'exigent les règles du produit), sans prolongation par les visites suivantes.                                                                                                      |

#148 a ajouté `room_bans` (§2.5). Le temps réel (#85) a ajouté `participants.connected` (présence, écrite seulement quand elle change) et `rooms.version` (incrémentée à chaque changement de la salle) ; voir le [guide du temps réel](realtime.fr.md#3-dans-le-code). Les parties closes ne dépendent plus des places (`game_players`, [guide des parties](games.fr.md)) : fermer une salle supprime les places avec elle (§2.6).

### 2.3 Génération du code

`generate_room_code()` (`app/services/rooms.py`) tire `ROOM_CODE_LENGTH` caractères de `ROOM_CODE_ALPHABET` avec `secrets.choice`. `RoomService.create` insère la salle dans un **savepoint** (`session.begin_nested()`) : quand l'insertion viole la contrainte d'unicité `uq_rooms_code`, seul le savepoint est annulé et un nouveau code est tiré, jusqu'à `ROOM_CODE_MAX_ATTEMPTS` (5) fois. Avec 32^6 (environ un milliard) de codes, une seule collision est déjà rare ; atteindre la limite est journalisé comme une erreur et répond `500`. Toute autre erreur d'intégrité remonte telle quelle.

### 2.4 Invités

Décidé et construit dans #87 (la question _Liens invités_ de la [roadmap](../product/roadmap.fr.md#questions-techniques)). Quelqu'un sans compte entre avec un **pseudo** (US-2.5) et retrouve sa place plus tard (US-5.4). Un invité n'est **jamais lié à un compte**.

- **Pseudo** : 1 à 50 caractères, espaces de début et de fin retirés (même règle que le nom affiché d'un compte). Unique dans la salle **sans tenir compte de la casse**, face à tous les noms affichés, invités et comptes : sinon `409` `nickname_taken`. L'index unique partiel soutient la règle entre invités ; quand il refuse un pseudo que le service a laissé passer (`lower()` de PostgreSQL et `str.lower()` de Python diffèrent sur quelques caractères Unicode), la réponse est le même `409`, pas une `500`. Un **compte** entre sans vérification de nom (US-2.4 : pas d'étape de plus) : il peut porter le nom d'un invité déjà présent ; le lobby les distingue par la mention « invité ».
- **Jeton** : `generate_guest_token` (`secrets.token_urlsafe`, 256 bits). Seul `hash_guest_token` (SHA-256) est gardé, dans `participants.guest_token_hash` (`app/core/security.py`).
- **Cookie** `guest_token` : `HttpOnly`, `SameSite=Strict`, `Secure` selon `AUTH_COOKIE_SECURE`, `Path` = `ROOM_COOKIE_PATH` + `/<code>` (par ex. `/api/rooms/K7P2QX`, le chemin vu par le navigateur à travers le proxy), `Max-Age` = la validité restante. Un cookie par salle : le navigateur ne l'envoie qu'aux routes de cette salle. Le navigateur est reconnu par ce cookie, **jamais par son adresse IP**.
- **Lien perso** : `FRONTEND_BASE_URL/r/<code>#guest=<jeton>`, renvoyé **une seule fois** par `POST /guests` (`guest_link`, `guest_link_expires_at`). `POST /guest-session {token}` rend la place sur n'importe quel appareil et y pose le cookie ; la validité n'est pas prolongée. Le lien n'est affiché qu'une fois, puisque seule son empreinte est gardée : un invité qui l'a perdu, toujours reconnu par son cookie, demande un **nouveau lien** (`POST /guest-link`). Un nouveau jeton remplace l'ancien, dont le lien et le cookie cessent de marcher ; la date d'expiration ne change pas.
- **Validité** : `GUEST_LINK_TTL_DAYS` depuis l'arrivée. Une place expirée est perdue (« Left ») : elle disparaît des participants, son cookie et son lien répondent `404`, et son pseudo redevient libre (la prochaine jonction d'un invité retire d'abord les places expirées de la salle). La fermeture d'une salle (§2.6) supprime ses places, donc leurs liens.
- **Lire la salle** : `GET /rooms/{code}` prend d'abord le compte (Bearer, vérifié comme partout : un token invalide répond `401` pour que le client rafraîchisse sa session), sinon le cookie d'invité de cette salle. Sans les deux, `404` `room_not_found`, comme un utilisateur sans place. Un invité n'est jamais room admin ; `PATCH /settings` et `POST /join` restent réservés aux comptes (`401`).
- Le canal temps réel (#85) authentifie les invités avec ce même cookie ([guide du temps réel](realtime.fr.md)).

### 2.5 Retrait et bannissement

Construit dans #148 (US-2.11, US-2.12).

- **Retrait** : `DELETE /rooms/{code}/participants/{participant_id}` (room admin seulement, `403` `room_admin_required` sinon) supprime la place, sous le verrou de la salle, à tout moment, partie comprise : ses placements sont supprimés avec la place (`ON DELETE CASCADE`, [guide des parties](games.fr.md#règles)). Un participant inconnu, ou un invité dont le lien a expiré, répond `404` `participant_not_found` ; la place du room admin lui-même, `409` `cannot_remove_room_admin`. La version est incrémentée ; après le commit, le service demande au canal de fermer les sockets de la personne (`4410` `removed_from_room`), **puis** publie `participant.removed` à la salle : le registre retire d'abord ses sockets, elle ne le reçoit donc pas. Le lien perso et le cookie d'un invité retiré cessent de marcher, puisque la place qui portait leur empreinte n'existe plus. Sans bannissement, la personne peut rejoindre à nouveau avec le lien ou le code.
- **Bannissement** : `?ban=true` écrit aussi une ligne `room_bans`, et les sockets se ferment avec `4411` `room_banned`. Pour un **compte**, la ligne porte `user_id` : `POST /join` répond `403` `room_banned`, quelle que soit la casse du code. Pour un **invité**, elle porte le `guest_token_hash` de la place : le navigateur garde son cookie `guest_token` (30 jours, chemin de la salle), qui part avec `POST /guests`, et ce navigateur reçoit le même `403`. C'est **au mieux** : une fenêtre privée ou des cookies effacés le contournent, puisque l'application n'utilise jamais l'adresse IP ; le room admin en est prévenu dans le dialogue, et verrouiller les arrivées pendant une partie l'arrête vraiment.
- **Option écartée** : tirer un nouveau code de salle à chaque bannissement d'invité. Tous les autres invités perdraient aussi leur place, puisque leurs cookies sont rangés sous le chemin de l'ancien code, et le lien partagé ne marcherait plus.
- **Débannissement** : `DELETE /rooms/{code}/bans/{ban_id}` (room admin seulement ; `404` `ban_not_found`). Seul le room admin voit les bannissements (`bans` dans `RoomResponse`, vide pour les autres) : la version de la salle ne change pas et rien n'est publié.
- **Nom affiché** : le bannissement garde le nom au moment du bannissement, le seul nom qu'un invité ait jamais eu.

### 2.6 Fermer une salle

Construit dans #89 (US-2.7), fermeture automatique dans #90 (US-2.8).

- **Route** : `DELETE /rooms/{code}` (room admin seulement, `403` `room_admin_required` sinon ; `404` `room_not_found`) répond `204`. `GameService.close_room` la traite sous le verrou de la salle, en une transaction.
- **Partie en cours** : elle est close d'abord (`_close_game`, [guide des parties](games.fr.md#26-cooldown-final)) : ses joueurs sont figés, ses placements ne dépendent donc plus des places sur le point d'être supprimées. Pendant un tour, le tour en cours se termine et les classements du moment deviennent les plateaux finaux (`_start_final_boards`) : la partie garde des résultats ; l'item interrompu ne donne pas de votes absents. Pendant le cooldown, les plateaux finaux restent tels quels. Le frontend demande une confirmation dans les deux cas, et dit quand une partie sera close d'abord.
- **Suppression** : la ligne de la salle est supprimée. La base supprime ses places et ses bannissements (`ON DELETE CASCADE`) et détache ses parties (`games.room_id` remis à `NULL`) : les parties survivent à leur salle (invariant 11). Le lien et le code ne marchent plus (`404` `room_not_found`), ni les liens perso et les cookies des invités (`404` `guest_link_invalid`).
- **Sockets** : après le commit, le service demande au canal de fermer tous les sockets de la salle avec `4412` `room_closed` (`RoomEventPublisher.close_room`) ; rien n'est publié, la salle n'existe plus. La page affiche « Le room admin a fermé cette salle. » avec un lien vers l'accueil ; le room admin qui l'a fermée revient à l'accueil.
- **Timers** : un timer encore programmé pour la partie ne trouve plus de salle (`_locked_room_of_game`) et ne fait rien.
- **Suppression de compte** : supprimer le compte d'un room admin ferme chacune de ses salles de la même façon, une fois la suppression confirmée et avant la suppression du compte (`AuthService.delete_account(before_delete=...)` avec `GameService.close_rooms_of_admin`, une transaction par salle). Sans cela, la base supprimerait les salles par `rooms.admin_id`, avec les placements d'une partie en cours, sans prévenir personne.
- **Fermeture automatique** (#90, US-2.8) : une salle ouverte où personne n'est connecté, et qui n'a pas changé depuis `ROOM_INACTIVITY_HOURS` (24 h par défaut), est fermée de la même façon. « Changé » se lit dans `rooms.updated_at`, qui bouge avec chaque `version` (une arrivée, un départ ou une déconnexion, les réglages, une partie) : le délai part donc du départ du dernier participant ; le heartbeat n'écrit rien, un participant connecté qui ne fait rien garde donc la salle ouverte. Une salle en partie n'est jamais fermée pour inactivité (cycles de vie : Playing → Closed seulement par le room admin).
- **Balayage** : `room_sweeper` (`app/services/room_sweeper.py`), lancé par le lifespan d'`app/main.py`, exécute `GameService.close_inactive_rooms` toutes les `ROOM_INACTIVITY_SWEEP_MINUTES` (15 par défaut) dans le threadpool, avec une session courte. Il tourne dans le processus qui tient les sockets, puisqu'il les ferme (`4412`) ; un script cron ne le pourrait pas. `list_inactive_room_ids` lit les candidates, puis chaque salle est revérifiée sous son verrou (quelqu'un a pu revenir) et fermée dans sa propre transaction. Le premier balayage arrive un intervalle après le démarrage : les participants connectés avant un redémarrage peuvent revenir d'abord. Un balayage en échec est journalisé et le suivant réessaie.

### 2.7 Réglages

| Variable                        | Rôle                                                                                                                         | Défaut       |
| ------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- | ------------ |
| `ROOM_DEFAULT_TIMER_SECONDS`    | Timer par item d'une nouvelle salle, en secondes (5 à 300)                                                                   | `30`         |
| `ROOM_DEFAULT_COOLDOWN_SECONDS` | Cooldown final d'une nouvelle salle, en secondes (10 à 600)                                                                  | `60`         |
| `GUEST_LINK_TTL_DAYS`           | Validité du lien perso et du cookie d'un invité, en jours depuis son arrivée (30 au plus)                                    | `30`         |
| `ROOM_COOKIE_PATH`              | Chemin des routes des salles vu par le navigateur, base du cookie des invités (`/rooms` dans les tests d'API, sans le proxy) | `/api/rooms` |
| `ROOM_INACTIVITY_HOURS`         | Une salle ouverte où personne n'est connecté, sans changement depuis ce nombre d'heures, est fermée (§2.6)                   | `24`         |
| `ROOM_INACTIVITY_SWEEP_MINUTES` | Intervalle du balayage qui ferme les salles inactives, en minutes                                                            | `15`         |

Les bornes sont des constantes (`app/constants/rooms.py`) : l'API valide les durées avec elles et les renvoie en params `ge` / `le`, que le frontend affiche sans les recopier. Les valeurs par défaut sont validées avec les mêmes bornes au démarrage de l'application.

### 2.8 Endpoints

Chaque route exige l'access token Bearer (`401` sinon), sauf les routes des invités et `GET /rooms/{code}` (§2.4).

| Méthode et chemin                                    | Corps                                                                                                   | Succès                             | Erreurs                           |
| ---------------------------------------------------- | ------------------------------------------------------------------------------------------------------- | ---------------------------------- | --------------------------------- |
| `POST /rooms`                                        | `{template_id}`                                                                                         | `201` `RoomResponse`               | `401`, `404`, `409`, `422`        |
| `GET /rooms/{code}`                                  | —                                                                                                       | `200` `RoomResponse`               | `401`, `404`                      |
| `POST /rooms/{code}/join`                            | —                                                                                                       | `200` `RoomResponse`               | `401`, `403`, `404`, `409`        |
| `POST /rooms/{code}/guests`                          | `{nickname}`                                                                                            | `201` `GuestRoomResponse` + cookie | `403`, `404`, `409`, `422`        |
| `POST /rooms/{code}/guest-session`                   | `{token}`                                                                                               | `200` `GuestRoomResponse` + cookie | `404`, `422`                      |
| `POST /rooms/{code}/guest-link`                      | —                                                                                                       | `200` `GuestRoomResponse` + cookie | `404`                             |
| `PATCH /rooms/{code}/settings`                       | `{item_order?, auto_advance?, timer_seconds?, cooldown_seconds?, admin_plays?, late_arrivals_allowed?}` | `200` `RoomResponse`               | `401`, `403`, `404`, `409`, `422` |
| `POST /rooms/{code}/game`                            | —                                                                                                       | `201` `RoomResponse`               | `401`, `403`, `404`, `409`        |
| `DELETE /rooms/{code}/participants/{participant_id}` | paramètre `ban` (`false` par défaut)                                                                    | `200` `RoomResponse`               | `401`, `403`, `404`, `409`, `422` |
| `DELETE /rooms/{code}/bans/{ban_id}`                 | —                                                                                                       | `200` `RoomResponse`               | `401`, `403`, `404`, `422`        |
| `DELETE /rooms/{code}`                               | —                                                                                                       | `204`                              | `401`, `403`, `404`               |

- `RoomResponse` vaut `{code, version, link, status, template: {id, name} | null, settings: {item_order, auto_advance, timer_seconds, cooldown_seconds, admin_plays, late_arrivals_allowed}, participants: [{id, display_name, is_admin, is_guest, connected}], is_admin, bans: [{id, display_name, is_guest}], game: {round_number, round_count, current_item: {id, text, image_url}, ends_at} | null, past_games: [{public_token, closed_at, player_count}]}` (la partie en cours, [guide des parties](games.fr.md)) ; `display_name` est le nom du compte ou le pseudo de l'invité, et les places d'invités expirées sont omises. `GuestRoomResponse` ajoute `guest_link` et `guest_link_expires_at`. `GET /rooms/{code}` accepte un compte ou un invité (§2.4) ; les autres routes exigent l'access token Bearer. `participants` sont dans l'ordre d'arrivée, le room admin d'abord ; `is_admin` indique si l'utilisateur qui fait la requête est le room admin ; `bans` n'est rempli que pour le room admin ; `past_games` liste les parties closes de la salle, de la plus récente à la plus ancienne, avec leur lien de résultats ([guide des résultats](results.fr.md#26-api-des-résultats)) ; `player_count` est calculé par la requête (`Game.player_count`, une `query_expression`), sans charger les joueurs.
- `PATCH /rooms/{code}/settings` et les routes de retrait et de débannissement verrouillent la ligne de la salle (`SELECT … FOR UPDATE`) jusqu'à leur commit, comme le [guide du temps réel](realtime.fr.md) le demande pour toute modification d'une salle.

### 2.9 Limites connues

- Parties : le démarrage (#91) pose `playing` et fige le template ([guide des parties](games.fr.md)) ; les tours, les placements et le retour pendant une partie y sont décrits.
- Une salle en partie que tout le monde a quittée, avec le réglage « tout le monde a placé », attend le room admin : personne de connecté ne termine jamais le tour, et une salle en partie n'est jamais fermée pour inactivité.
